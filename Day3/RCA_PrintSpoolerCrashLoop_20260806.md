## Section 1 — Event ID Reference: What Each Event Records

### Event ID 7034 — Service Terminated Unexpectedly (Source: Service Control Manager)

**Purpose:** Event 7034 is generated by the Windows Service Control Manager (SCM) each time a monitored service exits without being explicitly stopped by an authorised action (i.e., not via a Stop command, system shutdown, or controlled restart). It records the service name and a running count of how many times this unexpected termination has occurred since the service was last successfully started.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Service name | Print Spooler | The Windows service that manages print jobs and printer drivers (spoolsv.exe) |
| Termination count | 1, 2, 3 | Increments with each unexpected crash; helps distinguish isolated faults from a crash loop |
| Level | Error | The SCM classifies this as a system error, not a warning |

**What it does NOT record:** Event 7034 does not record the error code or reason for the termination. It only records the fact of unexpected exit and the count. To understand the specific fault, Event 7023 or an application crash event (Event 1000) is needed.

**Diagnostic Value:** The repeating count (1 → 2 → 3) with consistent ~31-second intervals between entries confirms that the SCM's configured recovery actions are automatically restarting the service after each crash, and the service is crashing again almost immediately on each restart attempt. This is the defining signature of a **crash loop**.

**Occurrence in this incident:** Fired three times:
- 10:01:14 (1st unexpected termination)
- 10:01:45 (2nd unexpected termination, +31 seconds)
- 10:02:16 (3rd unexpected termination, +31 seconds)

---

### Event ID 7031 — Service Terminated Unexpectedly with Recovery Action (Source: Service Control Manager)

**Purpose:** Event 7031 is closely related to 7034 but fires when the SCM has a **configured recovery action** associated with the failure and is about to execute it. It records both the termination count and the specific corrective action the SCM will take, along with the delay before that action is applied.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Service name | Print Spooler | Same service as Event 7034 |
| Termination count | 4 | Fourth unexpected crash — the recovery threshold that triggers a different action |
| Corrective action | Restart the service | SCM will attempt to start spoolsv.exe again |
| Delay | 60,000 milliseconds (60 seconds) | SCM waits 60 seconds before the restart attempt |

**Distinction from 7034:** Event 7034 fires for the first three failures (where, in this case, the recovery is configured with a shorter restart interval). Event 7031 fires for the fourth failure, which has a 60-second recovery delay — giving more detail about what recovery is being attempted.

**Diagnostic Value:** Confirms that Windows is attempting self-healing via automatic service restart. The 60-second delay before the restart attempt means the next service start attempt occurs at approximately 10:03:47, which aligns exactly with the timestamp of Event 7023 at 10:03:49.

**Occurrence in this incident:** Fired once at 10:02:47 (4th unexpected termination).

---

### Event ID 7023 — Service Terminated with Error (Source: Service Control Manager)

**Purpose:** Event 7023 is generated when a service terminates and returns a specific error code to the SCM. Unlike Event 7034 (which records only the fact of unexpected termination), Event 7023 records **why** the service terminated — the specific Windows error message or code returned by the service process on exit.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Service name | Print Spooler | The failing service |
| Error | The specified module could not be found | Windows error `ERROR_MOD_NOT_FOUND` (126) — a DLL or executable dependency required by the service cannot be located on the file system |

**What "The specified module could not be found" means:**
When the Print Spooler service starts, it loads its own executable (spoolsv.exe) and dynamically links against printer driver DLLs. If any required DLL is missing from the expected path — whether a core spooler DLL, a printer driver file, or a third-party print management module — Windows cannot resolve the dependency and the service terminates with error 126.

**Common causes in a Print Spooler context:**
- A printer driver was partially uninstalled, leaving orphaned registry entries pointing to non-existent DLLs
- A Windows security update (particularly PrintNightmare-related patches) quarantined or blocked a printer driver DLL
- A third-party print management application was removed, leaving its spooler extension DLL registered but deleted
- Manual file deletion or disk corruption removed a spooler dependency

**Diagnostic Value:** This is the **most important event in this incident**. It identifies the primary technical cause of the crash loop: a missing DLL dependency. Without this event, the investigation might focus only on the logon failure (Event 7038). Event 7023 confirms the crash loop was happening **before** the logon issue appeared, making the DLL the root crash cause.

**Occurrence in this incident:** Fired at 10:03:49, immediately after the 60-second recovery delay from Event 7031 expired and the SCM attempted to restart the service.

---

### Event ID 7038 — Service Logon Failure (Source: Service Control Manager)

**Purpose:** Event 7038 is generated when the SCM cannot start a service because the service's configured logon account fails authentication. The SCM records the account name, the specific logon failure reason, and the service name.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Service name | Print Spooler | The service that failed to start |
| Account | NT AUTHORITY\SYSTEM | The built-in LocalSystem account — the most privileged Windows account |
| Error | Logon failure: the user has not been granted the requested logon type at this computer | The account exists and is valid, but has been explicitly denied the specific type of logon (interactive, service, batch, network) required to run as a service |

**Why this is abnormal:** NT AUTHORITY\SYSTEM (LocalSystem) is the highest-privilege built-in account on Windows. It is granted the "Log on as a service" right by default on every Windows installation. If this account is being denied a logon type, one of the following has occurred:
- A Group Policy Object (GPO) has been applied that explicitly **denies** a logon right to SYSTEM (e.g., "Deny log on as a service" or "Deny log on locally")
- A security hardening script or CIS benchmark configuration has restricted logon rights
- A PrintNightmare-related Group Policy or registry change has specifically restricted the Print Spooler service's operating context
- The service account configuration in the SCM has been manually changed from LocalSystem to a different account, and the entry for NT AUTHORITY\SYSTEM is now inconsistent

**Compounding Effect:** Even if the missing DLL (Event 7023) were restored, the logon failure (Event 7038) would still prevent the service from starting. Both faults must be resolved simultaneously for the Print Spooler to recover.

**Occurrence in this incident:** Fired at 10:03:50 — one second after Event 7023, during the same restart attempt, indicating both failures occurred in the same start sequence.

## Section 2 — Sequence of Events: Plain English Reconstruction

The following is a chronological reconstruction of the Print Spooler crash loop on 2024-03-15.

**10:01:14** — The Print Spooler service (spoolsv.exe) terminates unexpectedly for the first time. The SCM logs **Event 7034** (count: 1). Based on the service's recovery configuration, the SCM restarts it automatically after a short delay (approximately 31 seconds based on subsequent event timing).

**10:01:45 (+31 seconds)** — The restarted Print Spooler crashes again immediately on startup. **Event 7034** fires again (count: 2). The SCM again triggers an automatic restart.

**10:02:16 (+31 seconds)** — The Print Spooler crashes a third time on startup. **Event 7034** fires (count: 3). Another automatic restart is triggered.

**10:02:47 (+31 seconds)** — The Print Spooler crashes a fourth time. This time the SCM logs **Event 7031** instead of 7034, because the fourth failure triggers a different recovery action: restart the service, but with a 60-second delay. The SCM schedules the next restart for 10:03:47.

**10:03:49 (~60 seconds later)** — The SCM attempts to restart the Print Spooler. This time, the service terminates immediately with a specific error: **"The specified module could not be found"** (**Event 7023**). This is the first time the SCM captures the actual error code. The service cannot load a required DLL file — a critical dependency is missing from the file system. The service exits before it can run.

**10:03:50 (one second later)** — During the same startup attempt, the SCM also records **Event 7038**: NT AUTHORITY\SYSTEM — the account the Print Spooler is configured to run as — has been denied the logon type required to start as a service. The service account is being blocked by a security policy or User Rights Assignment configuration.

**Result:** The Print Spooler enters a failed state. It cannot start because (a) a required DLL is missing and (b) even if the DLL were present, a security policy is blocking the service account logon. All print functionality is unavailable. The service cannot self-recover further.

**Key Diagnostic Pattern:**
- Crashes 1–4 occur at very regular ~31-second intervals → SCM auto-restart is cycling
- The gap between crash 4 (10:02:47) and the next attempt (10:03:49) is ~62 seconds → matches the 60-second recovery delay in Event 7031
- Event 7023 fires before 7038 in the same attempt → the DLL error is encountered first (service process start), the logon error is encountered during the same initialization sequence
- The earlier crashes (Events 7034) likely had the same underlying causes but the SCM only captured the error code on the later attempt after the 60-second restart

## Section 3 — Most Likely Cause with Evidence

### Primary Finding: Missing Printer Driver DLL Combined with Security Policy Stripping SYSTEM Logon Rights

**Conclusion Statement:** The Print Spooler crash loop is caused by two simultaneous failures: (1) a required printer driver or spooler extension DLL has been removed from the file system while its registry entry remains, causing the service to fail on load; and (2) a recent Group Policy change or security hardening action has removed NT AUTHORITY\SYSTEM's "Log on as a service" right, preventing the service from starting even if the DLL fault were corrected.

**Supporting Evidence:**

| # | Evidence | Analysis |
|---|---|---|
| 1 | **Events 7034 × 3 at 31-second intervals** | Regular restart cadence confirms SCM auto-recovery is cycling; service crashes immediately on each restart — the fault is persistent, not transient |
| 2 | **Event 7023: "The specified module could not be found"** | Windows error 126 (ERROR_MOD_NOT_FOUND) — a DLL registered to the Print Spooler cannot be located at its expected path; the registry entry exists but the file does not |
| 3 | **Event 7031 triggers 60-second recovery delay** | Fourth failure threshold reached; SCM's escalated recovery provides the time gap seen before Event 7023 fires |
| 4 | **Event 7038: NT AUTHORITY\SYSTEM logon denied** | LocalSystem is denied a logon type it holds by default — this is only possible if a GPO or local security policy explicitly removes or denies this right |
| 5 | **Events 7023 and 7038 fire 1 second apart** | Both failures occur in the same restart attempt — confirming both faults are active simultaneously and both must be resolved |
| 6 | **Crash loop begins at 10:01:14** | The Print Spooler was presumably running before this time; something changed at or before 10:01:14 — a driver uninstall, a GPO push, a Windows Update, or an admin action |

**Alternative Causes Considered:**

| Cause | Probability | Why Ranked Lower |
|---|---|---|
| Corrupted spoolsv.exe binary | 10% | Would generate a different error (hash mismatch, access denied) not "module not found" |
| Disk failure causing DLL to become unreadable | 8% | Would affect more services and generate disk I/O errors; no evidence of broader impact |
| Service configured with wrong account (not SYSTEM) | 15% | Possible, but Event 7038 explicitly states NT AUTHORITY\SYSTEM was the attempted account |
| Antivirus quarantining spooler DLL | 20% | Viable: AV tools sometimes quarantine printer driver DLLs; would explain "not found"; check AV quarantine logs |

## Section 4 — 5 Why Root Cause Analysis

### Problem Statement
> The Windows Print Spooler service (spoolsv.exe) enters a crash loop on 2024-03-15 at 10:01:14, crashing four times in rapid succession. After the SCM's recovery action attempts a restart, the service terminates with "The specified module could not be found" and NT AUTHORITY\SYSTEM is simultaneously denied the logon type required to run the service. All print functionality is lost.

---

### Why 1: Why did the Print Spooler enter a crash loop?

**Answer:** Because every time the Service Control Manager restarted the Print Spooler, the service process (spoolsv.exe) failed to start successfully and terminated immediately, causing the SCM to detect another unexpected termination and trigger another restart — a cycle with no successful start to break it.

**Evidence:**
- Event 7034 fires three consecutive times at consistent ~31-second intervals (10:01:14, 10:01:45, 10:02:16)
- Event 7031 fires on the fourth crash, confirming the SCM is executing its recovery sequence
- The service never reaches a running state between any of these events — it is crashing on startup, not during operation

**Key Distinction:** The crash loop is a symptom of the startup failure, not a separate problem. The service is not running and then crashing; it is failing before it can run at all.

---

### Why 2: Why did the Print Spooler fail to start on every restart attempt?

**Answer:** Because during the startup sequence, the Print Spooler attempted to load a registered DLL that could not be found on the file system, causing the process to exit immediately with Windows error 126 (`ERROR_MOD_NOT_FOUND`). Simultaneously, the service account (NT AUTHORITY\SYSTEM) was denied the required logon type, compounding the startup failure.

**Evidence:**
- Event 7023 (10:03:49): "The specified module could not be found" — confirms a DLL dependency is broken
- Event 7038 (10:03:50): NT AUTHORITY\SYSTEM denied logon type — confirms an account/policy fault
- Both events fire within 1 second of each other in the same restart attempt, proving both failures are active at the same time
- The earlier crashes (7034 ×3) almost certainly had the same underlying causes; Event 7023 only surfaced when the SCM captured the error code after the 60-second recovery delay

---

### Why 3: Why is a required DLL missing and why is SYSTEM's logon right denied?

**Answer (DLL Missing):** A registered printer driver or third-party print spooler extension DLL has been removed from the file system while its registration in the Windows registry (under `HKLM\SYSTEM\CurrentControlSet\Control\Print\Providers` or printer driver entries) was not cleaned up. The spooler attempts to load the DLL on startup, the OS cannot find the file, and the service exits.

**Answer (SYSTEM Logon Denied):** A Group Policy Object was applied to the machine that either (a) explicitly added NT AUTHORITY\SYSTEM to the "Deny log on as a service" User Rights Assignment, or (b) replaced the "Log on as a service" right with a restricted list that omits SYSTEM — overwriting the default. This is an uncommon but documented outcome of aggressive security hardening GPOs or CIS benchmark configurations that restrict logon rights without accounting for built-in system accounts.

**Evidence (DLL):**
- Error 126 specifically means the file path registered in the registry does not resolve to an accessible file
- Print Spooler is a known target for orphaned driver entries: printer driver uninstallers sometimes remove DLL files without cleaning registry references
- Windows PrintNightmare patches (CVE-2021-1675 / CVE-2021-34527) have been known to block certain printer driver DLLs via Point and Print restriction policies

**Evidence (Logon):**
- NT AUTHORITY\SYSTEM's "Log on as a service" right cannot be denied by default — it requires an explicit policy action
- The error message "the user has not been granted the requested logon type" is the standard User Rights Assignment denial message
- GPO application commonly pushes security baseline changes to multiple machines simultaneously, which would explain why the fault began at a specific time

---

### Why 4: Why was a printer driver DLL removed without cleaning its registry entry, and why was a GPO applied that incorrectly denied SYSTEM's logon right?

**Answer (DLL):** Because the printer driver was uninstalled using a method (manual file deletion, partial uninstaller, or forcible removal during a Windows Update) that did not invoke the Windows printer driver uninstallation API (`DeletePrinterDriver`), leaving orphaned registry entries. Alternatively, a security tool (antivirus, endpoint DLP, or patch management agent) quarantined or deleted the DLL file as part of a PrintNightmare remediation, without removing the associated registry entries.

**Answer (GPO):** Because the GPO that was applied to this machine was configured with a User Rights Assignment that overrides default settings and was not reviewed against the impact on built-in system accounts before deployment. Security hardening templates (CIS, DISA STIG, Microsoft Security Baseline) sometimes include "Log on as a service" restrictions intended to limit named service accounts, but can inadvertently strip rights from SYSTEM if the policy attribute is set to an explicit list rather than an additive grant.

**Contributing factors:**
- No pre-deployment testing of the GPO against a representative test machine with the same printer drivers installed
- No change management review that cross-checked the security baseline against the Print Spooler service dependency
- The printer driver removal (by whatever mechanism) may have been part of a broader remediation effort (PrintNightmare patch, driver consolidation) that was not tested end-to-end
- No monitoring of Event 7038 or User Rights Assignment changes that would have caught the SYSTEM logon denial when the GPO was first applied

---

### Why 5: Why were there no controls in place to detect or prevent these two configuration failures before they caused a service outage?

**Answer:** Because the organisation lacks formal change validation processes for both Group Policy deployments and printer driver management, does not perform pre-deployment testing of GPOs against workload-representative test machines, and does not proactively monitor for Service Control Manager error events (7023, 7034, 7038) that would surface service configuration failures before users report loss of functionality.

**Systemic gaps identified:**

| Gap | Description | Risk |
|---|---|---|
| **No GPO pre-deployment testing** | Security baseline GPOs are applied to production machines without first being validated on a representative test machine with the same software configuration | A single misconfigured User Rights Assignment can break system services on every machine the GPO targets |
| **No printer driver lifecycle process** | No documented procedure for the complete lifecycle of printer driver installation and removal, including registry cleanup validation after uninstallation | Orphaned registry entries accumulate over time, creating latent crash triggers activated by service restarts |
| **No SCM event monitoring** | Events 7034, 7031, 7023, and 7038 are not aggregated or alerted on by the SIEM or monitoring platform | IT discovers service failures only when users report them, not at the moment the failure begins |
| **No User Rights Assignment change alerting** | Changes to "Log on as a service," "Deny log on as a service," and similar rights are not audited or alerted | A GPO change can silently break service accounts without any notification to the infrastructure team |
| **No print service health check** | No scheduled or event-driven test that verifies the Print Spooler can start and reach a running state after system changes | Startup failures are not detected until a user attempts to print |
| **No PrintNightmare remediation validation** | If the DLL removal was part of a PrintNightmare patch or hardening effort, the post-remediation state of the Print Spooler was not validated before the change was signed off | Security remediations that affect the spooler require explicit verification that printing remains functional |

**Root Cause Statement:**
> The Print Spooler crash loop was caused by two simultaneous configuration failures: (1) a printer driver or spooler extension DLL was removed from the file system (likely by an incomplete uninstallation, security tool quarantine, or PrintNightmare remediation) while its registry entry was left intact, causing ERROR_MOD_NOT_FOUND on every startup; and (2) a Group Policy change stripped NT AUTHORITY\SYSTEM of the "Log on as a service" right, preventing the service from starting even if the DLL were restored. Both failures reached production because there are no pre-deployment validation controls for GPO deployments or printer driver lifecycle management, and no proactive monitoring for SCM error events.

## Section 8 — Lessons Learned

1. **Event 7023 is the key to diagnosing service crash loops.** Events 7034 and 7031 record *that* a service crashed; only Event 7023 records *why*. Always wait for or locate Event 7023 before concluding a diagnosis.

2. **NT AUTHORITY\SYSTEM being denied a logon right is never a default condition.** If Event 7038 names SYSTEM as the denied account, a deliberate policy change has occurred. Investigate GPO history, not service account configuration.

3. **Two simultaneous faults require both to be resolved.** Restoring only the missing DLL will leave the logon failure in place; fixing only the logon right will leave the DLL fault active. Both must be corrected before the service can start.

4. **Regular crash intervals reveal SCM auto-recovery behaviour.** A ~31-second crash cycle is the SCM restarting the service; this is not a timing coincidence. Use the interval to determine the configured recovery delay and trace back to the SCM service recovery settings.

5. **PrintNightmare remediations must be validated end-to-end.** Security patches and hardening actions targeting the Print Spooler are a common cause of post-remediation spooler failures. Any action that modifies printer drivers, User Rights Assignments, or spooler registry entries must include a print functionality test before sign-off.

6. **Proactive SCM event monitoring pays dividends.** The four crashes occurred over 95 seconds before the specific fault was surfaced. A SIEM alert on Event 7034 with a count threshold (e.g., ≥2 in 5 minutes) would notify IT at 10:01:45 — before users could report the issue.

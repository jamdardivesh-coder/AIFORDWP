## Section 1 — Event ID Reference: What Each Event Records

### Event ID 56 — Terminal Server Security Layer Protocol Error (Source: TermDD)

**Purpose:** Event 56 is generated by the TermDD (Terminal Device Driver) component of the Windows Remote Desktop Services stack when the RDP **security layer** detects an error in the protocol stream during connection establishment and forcibly terminates the connection. This event fires at the transport/security layer, below the application logon layer.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Source | TermDD | The kernel-mode terminal services driver, responsible for the RDP protocol transport |
| Level | Error | The connection was abnormally terminated, not gracefully closed |
| Client IP | 10.10.5.44 | The IP address of the RDP client that was disconnected |

**Technical Context:** When Network Level Authentication (NLA) is enabled on an RDP server (the modern default), credential validation occurs **before** the full remote session is established. If the user's credentials are rejected by NLA, the TermDD security layer considers this a protocol-level fault and generates Event 56 to record the forced disconnection. This is a protective mechanism — it ensures unauthenticated users cannot consume server resources by establishing a partial session.

**Diagnostic Value:** Event 56 is a symptom indicator, not a root cause event. Its presence confirms NLA is enforced and authentication failed at the transport layer. It should always be investigated alongside Event 140 and the corresponding Security log event (4625 or 4771) to determine the specific authentication failure reason.

**Occurrence in this incident:** Fired once at 14:01:02, coinciding with the first RDP authentication failure.

---

### Event ID 140 — RDP Connection Authentication Failure (Source: RemoteDesktopServices-RdpCoreTS)

**Purpose:** Event 140 is generated by the RemoteDesktopServices-RdpCoreTS provider — the user-mode RDP core service — when an inbound RDP connection attempt is rejected specifically because the supplied credentials (username or password) are incorrect. This event is the RDP service's own record of the authentication failure, separate from the Windows Security audit log.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Source | RemoteDesktopServices-RdpCoreTS | The core RDP service component (user-mode) |
| Level | Warning | Connection was refused due to authentication, not a system fault |
| Client IP | 10.10.5.44 | The connecting client's IP address |
| Reason | Username or password is not correct | Credential validation failed — the supplied credentials did not match any valid account or the password was wrong |

**Distinction from Event 56:** Event 56 fires at the kernel/transport layer (TermDD); Event 140 fires at the service/application layer (RdpCoreTS). When both fire at the same timestamp for the same client IP, this confirms the failure is specifically a credential rejection during NLA pre-authentication — not a network or certificate error.

**Diagnostic Value:** Event 140 provides a human-readable description of the authentication failure reason, making it useful for first-line triage. However, it does not record the account name attempted. Event 4625 in the Security log must be cross-referenced to identify the account.

**Occurrence in this incident:** Fired once at 14:01:02, simultaneous with Event 56 — confirming both events are records of the same first failed authentication attempt.

---

### Event ID 4625 — Failed Account Logon (Source: Security)

**Purpose:** Event 4625 is a Windows Security Audit event generated every time an account fails to log on to the system, regardless of the protocol or method. It is the definitive record of a failed authentication attempt in the Windows Security log. Event 4625 requires the "Audit Logon Events" or "Audit Account Logon Events" policy to be enabled.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Account | FINBRIDGE\bwalker | The domain account whose credentials were presented and rejected |
| Failure reason | Unknown username or bad password | The authentication system could not match the credentials — either the username does not exist or the password is incorrect |
| Logon type | 10 (RemoteInteractive) | Logon type 10 specifically identifies an RDP/Terminal Services session — the user is logging on remotely via Remote Desktop |
| Source IP | 10.10.5.44 | The IP address from which the logon attempt originated |
| Level | Audit Failure | The Windows Security auditing system classifies this as a failure audit |

**Logon Type 10 Significance:** Logon type 10 (RemoteInteractive) is exclusively used for Remote Desktop connections. Its presence confirms this is an RDP authentication event, not a network share (type 3), scheduled task (type 4), or local console (type 2) logon.

**Diagnostic Value:** Event 4625 is the key security audit record for failed logon attempts. Multiple Event 4625 entries for the same account from the same source IP in a short timeframe are the primary indicator of either a user entering their password incorrectly (fat-finger, Caps Lock, forgotten password) or a credential-stuffing/brute-force attack. Context — consistent IP, known account name, eventual successful logon — distinguishes user error from attack.

**Occurrence in this incident:** Fired three times:
- 14:01:04 (1st failure — FINBRIDGE\bwalker)
- 14:03:18 (2nd failure — +2 min 14 s)
- 14:05:33 (3rd failure — +2 min 15 s)

The consistent ~2-minute intervals between attempts suggest a human user retrying manually (not an automated brute-force tool, which would attempt credentials in milliseconds).

---

### Event ID 4740 — User Account Locked Out (Source: Security)

**Purpose:** Event 4740 is generated by the Windows Security auditing system when an account is locked out because the number of consecutive bad-password attempts has reached the threshold defined by the domain's Account Lockout Policy. Once locked out, all further logon attempts — even with the correct password — will fail until the account is unlocked by an administrator or the lockout duration expires.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Account | FINBRIDGE\bwalker | The account that has been locked out |
| Caller computer | 10.10.5.44 | The computer (by IP or hostname) from which the failed attempts that caused the lockout originated |
| Level | Audit Failure | Classified as a failure audit event by the security system |

**Account Lockout Policy Context:** In a typical Active Directory environment, the Account Lockout Policy defines:
- **Account lockout threshold:** The number of failed attempts before lockout (in this incident: 3, based on lockout occurring after exactly 3 Event 4625 entries)
- **Account lockout duration:** How long the account remains locked before automatically unlocking (0 = never auto-unlock; common values: 15, 30, or 60 minutes)
- **Observation window:** The time window within which failures are counted

**Diagnostic Value:** Event 4740 is critical for security monitoring. It can indicate either a user who has forgotten their password or an active credential attack against a known account. The "Caller computer" field helps identify the source machine, which is essential for both user support (is this the user's own machine?) and security investigation (is this an unknown or unexpected source?).

**Occurrence in this incident:** Fired once at 14:05:34 — one second after the 3rd Event 4625, confirming the lockout threshold is 3 failed attempts and the lockout took effect immediately.

---

### Event ID 131 — RDP TCP Connection Accepted (Source: RemoteDesktopServices-RdpCoreTS)

**Purpose:** Event 131 is an informational event generated when the RDP server successfully accepts a new TCP connection from a client at the network layer. This is the very first step of the RDP connection process — TCP socket establishment — and occurs **before** any authentication takes place. Its presence does not indicate a successful logon.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Source | RemoteDesktopServices-RdpCoreTS | The core RDP service |
| Level | Info | Not an error — TCP connection was accepted normally |
| Client | 10.10.5.44:52341 | Client IP and ephemeral source port; confirms a new TCP session from the same user machine |

**Diagnostic Value:** Event 131 is useful for confirming that network connectivity to the RDP server was established. Its presence followed by a successful Event 4624 (with no intervening 4625 failures) confirms the lockout was resolved and the user authenticated with the correct credentials on this attempt. The new source port (52341) confirms this is a fresh TCP session — not a continuation of the earlier failed sessions.

**Occurrence in this incident:** Fired at 14:22:07 — 16 minutes 33 seconds after the lockout at 14:05:34. This timing is consistent with either an automatic account unlock after a policy-defined lockout duration or a manual unlock by an IT administrator.

---

### Event ID 4624 — Successful Account Logon (Source: Security)

**Purpose:** Event 4624 is generated by the Windows Security auditing system when an account successfully authenticates and a logon session is created. It is the counterpart to Event 4625 (failed logon) and confirms that the full authentication process completed successfully.

**Key Fields and Their Meaning:**

| Field | Value | Meaning |
|---|---|---|
| Account | FINBRIDGE\bwalker | The domain account that successfully authenticated |
| Logon type | 10 (RemoteInteractive) | Confirms this is an RDP session logon |
| Source IP | 10.10.5.44 | Same IP as the failed attempts — confirms this is the same user resolving their earlier access issue |
| Level | Audit Success | Classified as a success audit by the security system |

**Diagnostic Value:** Event 4624 closes the incident timeline — it confirms the account lockout was resolved (either by auto-unlock or admin intervention), the user supplied the correct credentials, and RDP access was successfully established. The 2-second gap between Event 131 (TCP accepted, 14:22:07) and Event 4624 (logon success, 14:22:09) is normal for NLA authentication latency.

**Occurrence in this incident:** Fired at 14:22:09 — closing the 17-minute outage window that began at lockout (14:05:34).

## Section 2 — Sequence of Events: Plain English Reconstruction

The following is a chronological reconstruction of the RDP connection failure and account lockout on 2024-03-15.

**14:01:02** — User bwalker, connecting from IP address 10.10.5.44, attempts to open a Remote Desktop (RDP) session to the FINBRIDGE domain server. The RDP client presents credentials during the Network Level Authentication (NLA) pre-authentication phase. The credentials are rejected — the password supplied does not match the password for FINBRIDGE\bwalker in Active Directory. The RDP server's security layer (TermDD) detects the authentication failure and disconnects the client (**Event 56**). The RDP core service simultaneously records the rejection (**Event 140**). Two seconds later, the Windows Security audit log records the first failed logon attempt (**Event 4625**, count 1).

**14:03:18** — Approximately two minutes and fourteen seconds later, bwalker attempts to connect again from the same IP address. The credentials are again incorrect. A second failed logon is recorded (**Event 4625**, count 2). The ~2-minute gap between attempts is consistent with a human user manually retrying after a connection failure dialogue, not an automated attack tool.

**14:05:33** — A further two minutes and fifteen seconds later, bwalker makes a third attempt. The credentials are again rejected. A third failed logon is recorded (**Event 4625**, count 3).

**14:05:34 (one second later)** — The third consecutive failure exhausts the domain's Account Lockout Policy threshold (3 failed attempts). Active Directory locks the FINBRIDGE\bwalker account. **Event 4740** is generated, recording the lockout and identifying 10.10.5.44 as the source computer. From this moment, even if bwalker enters the correct password, all logon attempts will fail with "Account locked out" until the account is unlocked.

**14:05:34 — 14:22:07 (16 minutes 33 seconds)** — The account remains locked. It is likely that during this period one of the following occurs:
- bwalker contacts the IT Service Desk or helpdesk to report being locked out, and an administrator unlocks the account (and possibly resets the password), or
- The domain's Account Lockout Duration policy timer expires and the account automatically unlocks

**14:22:07** — The RDP server accepts a new TCP connection from 10.10.5.44 (**Event 131**). This is a fresh session (new source port 52341), confirming bwalker is making a new connection attempt.

**14:22:09 (two seconds later)** — bwalker authenticates successfully using the correct credentials. **Event 4624** is generated, confirming a successful RemoteInteractive logon. The RDP session is established and bwalker can access the remote desktop.

**Total impact duration:** ~17 minutes of inability to access the remote system (from lockout at 14:05:34 to successful logon at 14:22:09).

## Section 3 — Most Likely Cause with Evidence

### Primary Finding: Legitimate User Entered Incorrect Password Repeatedly, Triggering Account Lockout Policy

**Conclusion Statement:** User bwalker manually entered incorrect RDP credentials on three consecutive attempts over approximately four and a half minutes from their own workstation (10.10.5.44), exhausting the three-attempt account lockout threshold. The account was locked by Active Directory, preventing access for approximately 17 minutes until the lockout was resolved. The eventual successful logon from the same IP with the same account confirms this was not a malicious attack.

**Supporting Evidence:**

| # | Evidence | Analysis |
|---|---|---|
| 1 | **Single consistent source IP (10.10.5.44) for all events** | All failures and the eventual success originate from the same IP; consistent with one user on one machine, not a distributed attack |
| 2 | **~2-minute intervals between Event 4625 failures** | Human retry timing — automated brute-force tools attempt thousands of credentials per second; 2-minute gaps indicate a user reading the error, reconsidering their password, and manually retrying |
| 3 | **Exactly 3 failures before lockout (Event 4740)** | The lockout occurred at the policy threshold; the user did not stop after 1 or 2 failures, suggesting genuine belief their next attempt would succeed |
| 4 | **Account: FINBRIDGE\bwalker — a valid domain account** | The account exists in Active Directory (it was locked out and later logged in successfully); this is not a probe for non-existent accounts |
| 5 | **Logon type 10 (RemoteInteractive) on all events** | Consistently RDP — no mixed logon types that might suggest credential stuffing across multiple services |
| 6 | **Successful Event 4624 from same IP 17 minutes later** | The user (or someone with the correct credentials) returned and authenticated successfully; if this were an attacker, the 17-minute wait with eventual success would be unlikely |
| 7 | **No Events 56 or 140 before the lockout period ended** | No further RDP connection attempts were made during the lockout period; consistent with a user who has accepted they are locked out and is waiting or seeking assistance |

**Most Probable Scenarios (ranked):**

| Rank | Scenario | Probability | Reasoning |
|---|---|---|---|
| 1 | User forgot password after a recent password change | 55% | Password changes are the most common trigger for subsequent lockouts; users sometimes type the old password from muscle memory |
| 2 | Caps Lock or keyboard language issue causing incorrect password | 25% | A common source of consistent password failures where the user believes they are typing correctly |
| 3 | RDP client had a cached/saved incorrect password | 15% | Windows Credential Manager or the RDP client may have stored a previous (now-changed) password and auto-submitted it |
| 4 | User was logging in to the wrong domain or used wrong username format | 5% | Unlikely given account FINBRIDGE\bwalker is valid and the eventual login succeeded with the same account |

**Attack Assessment — Low Confidence of Malicious Activity:**
The event pattern is inconsistent with a brute-force or credential-stuffing attack: single source IP, consistent target account, human-paced retry intervals, small number of attempts, and eventual successful logon from the same source. If this were an external attack, the source IP (10.10.5.44, a private RFC 1918 address in the 10.0.0.0/8 range) indicates it originates from within the internal network — either from bwalker's own workstation or from an internal host. This further reduces the likelihood of malicious external activity.

## Section 4 — 5 Why Root Cause Analysis

### Problem Statement
> User FINBRIDGE\bwalker was unable to establish an RDP connection to a FINBRIDGE domain system on 2024-03-15. Three consecutive failed authentication attempts at 14:01:04, 14:03:18, and 14:05:33 triggered the Account Lockout Policy, locking the account at 14:05:34. The user was locked out for approximately 17 minutes. Access was restored at 14:22:09.

---

### Why 1: Why was the user unable to connect via RDP?

**Answer:** Because the user's Active Directory account (FINBRIDGE\bwalker) was locked out by the domain's Account Lockout Policy after three consecutive failed authentication attempts. A locked-out account cannot authenticate to any domain resource regardless of whether the correct password is subsequently supplied.

**Evidence:**
- Event 4740 (14:05:34): FINBRIDGE\bwalker locked out, source 10.10.5.44
- Events 4625 × 3: Three consecutive Audit Failure entries for FINBRIDGE\bwalker at 14:01:04, 14:03:18, 14:05:33
- No further connection events between 14:05:34 and 14:22:07 — confirms complete access denial during lockout period
- Event 4624 (14:22:09): Successful logon only occurs after the 17-minute lockout gap — confirming the lockout was the barrier to access

---

### Why 2: Why was the account locked out?

**Answer:** Because the user entered an incorrect password on three consecutive RDP logon attempts within the observation window defined by the domain's Account Lockout Policy. The policy is designed to protect against password-guessing attacks by locking the account after a configured number of failures — in this case, the threshold is 3 attempts.

**Evidence:**
- Event 4625 (14:01:04): 1st failed logon — "Unknown username or bad password" — Logon type 10 from 10.10.5.44
- Event 4625 (14:03:18): 2nd failed logon — same account, same reason, same source
- Event 4625 (14:05:33): 3rd failed logon — same pattern
- Event 4740 (14:05:34): Lockout triggered 1 second after the 3rd failure — confirming threshold = 3
- Consistent ~2-minute intervals between failures indicate manual human retries, not automated tooling

---

### Why 3: Why did the user enter an incorrect password three times?

**Answer:** Because the user did not have the correct current password available at the time of the logon attempts. The most probable underlying reason is one of the following:
- **(a) Recent password change:** The user's password was recently changed (by the user or by an admin-forced reset), and the user was typing their previous password from memory or from a cached credential store
- **(b) Incorrect keyboard state:** Caps Lock was active, a keyboard language layout was incorrect, or a special character was mistyped, making the user believe they were entering the correct password while the actual string submitted was different
- **(c) Saved/cached incorrect credential:** The user's RDP client or Windows Credential Manager had a stored, now-outdated password and was auto-submitting it without the user realising

**Evidence:**
- The user attempted three times — suggesting genuine belief the next attempt would succeed (consistent with typing confidence, not forgotten password)
- The ~2-minute gaps suggest the user paused, re-read the password (possibly from a note or memory), and retried — not that they instantly knew the correct one
- The eventual successful logon 17 minutes later from the same IP and same account confirms the user (or IT) was able to supply the correct credentials — meaning the password was not truly unknown, only temporarily unavailable or incorrectly entered

---

### Why 4: Why did the user not have the correct password readily available or realise they were entering it incorrectly?

**Answer:** Because there is no enforced mechanism to ensure users are informed of or retain their correct credentials after a password change event. Contributing factors include:

| Factor | Detail |
|---|---|
| **No password change notification process** | If an admin forced a password reset, there is no confirmation that the user received and acknowledged the new temporary password before their session was closed |
| **No pre-RDP credential verification** | Users can attempt RDP logons without any prior check that their credentials are current; the first indication of a problem is the logon failure itself |
| **No Caps Lock or keyboard state warning in RDP client** | The Windows RDP client does not alert the user that Caps Lock is active before submitting credentials, unlike the Windows lock screen which displays a Caps Lock indicator |
| **No cached credential expiry notification** | Windows Credential Manager silently retains old saved passwords; when a password changes, stored credentials are not automatically purged or flagged as stale |
| **No self-service password reset available at point of failure** | If the user was locked out because of a forgotten or changed password, there was no self-service portal accessible without first being able to log in, creating a dependency on the IT helpdesk for resolution |

---

### Why 5: Why are there no controls in place to prevent repeated lockouts from this cause, or to resolve them more quickly?

**Answer:** Because the organisation lacks a combination of user-facing password management tools and IT monitoring processes that would either prevent the lockout from occurring or reduce the resolution time when it does.

**Systemic gaps identified:**

| Gap | Description | Risk |
|---|---|---|
| **No self-service password reset (SSPR)** | Users who are locked out or have forgotten their password must call the IT helpdesk; they cannot self-serve. This creates helpdesk dependency and extends resolution time | Every lockout requires IT intervention; resolution time is bounded by helpdesk availability and queue depth |
| **No proactive lockout alerting** | Event 4740 is not monitored or alerted on in real time; IT becomes aware only when users call | By the time IT is notified, the user has already been locked out and the disruption has begun |
| **No forced-reset user communication process** | When an admin resets a user's password, there is no verified communication step to confirm the user received and understood the new temporary credentials before their session ended | Users return to log in with the old password, triggering the lockout cycle |
| **No RDP pre-authentication credential health check** | No tooling warns the user that their stored RDP credentials may be stale (e.g., following a password change, Credential Manager is not automatically updated) | Users encounter lockout without warning |
| **No threshold escalation policy** | Three failed attempts is a low lockout threshold. While it provides good brute-force protection, it offers very little tolerance for legitimate user error. A policy review to consider whether 5 attempts would better balance security and usability has not been conducted | Legitimate users are locked out on minor errors (typo, Caps Lock) as readily as attackers are blocked |
| **No account lockout dashboard** | No central view of lockout events across the estate; IT cannot see patterns such as a specific user locking out repeatedly (suggesting a cached credential problem) or a specific machine causing lockouts for multiple users (suggesting compromise) | Systemic issues are not visible; each lockout is handled as an isolated ticket |

**Root Cause Statement:**
> The immediate cause of the RDP failure was user bwalker entering incorrect credentials three times, triggering the Account Lockout Policy. The underlying cause is that the user did not have access to the correct current password at the time of the attempts — most likely due to a recent password change where the new credentials were not confirmed as received, or a keyboard state issue. The systemic root cause is the absence of self-service password reset capability and real-time lockout monitoring, which together mean that any lockout requires helpdesk intervention and carries a recovery time measured in minutes to hours rather than seconds.

## Section 9 — Lessons Learned

1. **Three failed attempts at 2-minute intervals is a user, not an attacker.** Brute-force tools do not pause for 2 minutes between attempts. Interval analysis is one of the fastest ways to distinguish user error from credential attack.

2. **Event 56 and Event 140 are symptoms; Event 4625 is the record.** Events 56 and 140 only appear on the first connection attempt in this incident. The Security log Event 4625 is the consistent, countable record across all three failures. Always cross-reference both logs.

3. **The 17-minute resolution gap is a service metric, not just a timeline detail.** A 17-minute outage from a password lockout is preventable with SSPR. Every minute of that gap is wasted productivity and a helpdesk cost.

4. **Event 4740 fires after the damage is done.** Monitoring Event 4625 with a count threshold (≥2 in 5 minutes for the same account) would alert IT before the lockout — enabling proactive intervention (call the user) before Event 4740 fires.

5. **Internal source IPs should always be validated.** IP 10.10.5.44 is an internal RFC 1918 address. Before closing as user error, confirm the IP belongs to bwalker's assigned workstation. An internal attacker using a compromised internal host would present exactly the same event signature.

6. **Cached RDP credentials are a silent lockout trigger.** If bwalker had saved credentials in the RDP client or Credential Manager, these would auto-submit silently on connection — consuming failure attempts without any user action. Clearing cached credentials after a password change must be part of the password reset procedure.

# Incident Analysis and Ranked Hypotheses

## Scope Facts (as provided)
- Symptom: Intune Win32 app install failed for Adobe Acrobat Pro v23.6
- Installer context: SYSTEM
- Package: AdobeAcrobatPro.intunewin
- Install command: msiexec /i AcrobatPro.msi /quiet
- Primary error: MSI return code 1603
- Detection rule used: Registry key check
  - Key: HKLM\SOFTWARE\Adobe\Acrobat Reader\23.0
  - Result: Value not found, Not detected
- Behavior: Initial failure followed by retry after 60 minutes; retry also failed with 1603

## Ranked Likely Causes (most probable first)

### 1. Packaging/install command issue inside the .intunewin payload
Why this fits the scope facts:
- Return code 1603 is a generic fatal MSI failure and commonly appears when command-line assumptions do not match packaged content.
- Command uses only `AcrobatPro.msi` and does not show an explicit working path, transform, or prerequisite chain that Adobe enterprise installers often require.
- Same code on immediate retry suggests deterministic install failure rather than transient network fluctuation.

Single fastest check:
- Run the exact command manually as SYSTEM with full logging:
  - `msiexec /i "AcrobatPro.msi" /qn /L*v C:\Windows\Temp\AcrobatPro_Install.log`
  - Review the final `Return value 3` block in the MSI log.

### 2. Incorrect deployment content model for Adobe package (MSI-only vs setup/bootstrap requirement)
Why this fits the scope facts:
- Many Adobe Acrobat Pro enterprise deployments require `setup.exe` generated by the Adobe Customization Wizard/Enterprise Toolkit rather than direct MSI execution.
- If the MSI expects resources not present in the working directory, install fails with 1603.

Single fastest check:
- Extract the Intune package source and verify whether Adobe setup payload files (for example `Setup.ini`, CABs, and support folders) are present and referenced by the install command.

### 3. Existing Adobe product state conflict (upgrade/downgrade/product code collision)
Why this fits the scope facts:
- MSI 1603 frequently occurs when an installed product or remnants conflict with the target package.
- Acrobat Reader/Acrobat Pro coexistence or channel mismatch can block install.
- Detection points to `Acrobat Reader\23.0`, which may indicate product family mismatch between what is installed and what is being deployed.

Single fastest check:
- On an affected endpoint, inventory installed Adobe products and product codes from:
  - `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall`
  - `HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall`

### 4. System context permission/path constraint during install execution
Why this fits the scope facts:
- Install runs as SYSTEM; if package extracts to a path with access issues, or required folders/services are unavailable, MSI can fail with 1603.
- Repeated failure in same context can reflect a consistent local execution constraint.

Single fastest check:
- Validate IME cache extraction path and ACLs, and confirm SYSTEM can read full source and write to target locations (Program Files, ProgramData, temp).

### 5. Detection rule mismatch causing false-negative post-install status (secondary issue)
Why this fits the scope facts:
- Detection checks `Acrobat Reader` path while app is `Acrobat Pro`.
- This mismatch can mark a successful install as failed if install actually succeeds.
- In this case, 1603 indicates a real installer failure still exists, but detection mismatch may also be present and should be corrected.

Single fastest check:
- Validate expected post-install registry/product evidence for Acrobat Pro and align detection to that exact artifact.

## Current Position
- This is a ranked hypothesis list only.
- Root cause is not yet confirmed.
- Available evidence strongly indicates a real installer failure (1603), with a possible parallel detection rule design issue.
